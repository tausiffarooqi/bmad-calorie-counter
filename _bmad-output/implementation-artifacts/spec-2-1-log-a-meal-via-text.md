## Intent

**Problem:** Nothing in the app can turn a free-text meal description into a calorie estimate yet — there's no `EstimationProvider` port, no Gemini integration, no `entries` table, and the Daily-view placeholder's "Add Text" button does nothing.

**Approach:** Establish the `EstimationProvider` port + `GeminiAdapter` (AD-2), the `entries` table, and a `POST /api/entries` route; wire the placeholder's "Add Text" button to a minimal Dialog (shadcn, unmodified defaults) that submits a description, shows a bare in-progress state while waiting, and either succeeds with a calorie count or shows a plain retry message on insufficient detail. Story 2.3 owns the polished in-progress/failure treatment — this story only needs *a* working state for each, not the final one.

</frozen-after-approval>

## Boundaries & Constraints

**Always:** All `entries` writes go through `lib/services/entries.ts` — never a direct DB call from the route handler (AD-1). `estimate()`'s `{ ok: false, reason: 'insufficient_detail' }` is a return value, never a thrown exception (AD-2) — only genuine call failures (network, API error) throw. The API route sets `export const maxDuration = 60` (AD-9) and shows an in-progress state for the full duration of the pending call, however long it takes — no client-side timeout. `GeminiAdapter` calls the model via the `gemini-flash-lite-latest` alias (→ `gemini-3.5-flash-lite`) — renegotiated with the human 2026-09-21 (AD-2 amended in `ARCHITECTURE-SPINE.md`): the originally-planned `gemini-flash-latest`/`gemini-3.8-flash` full tier hit persistent 503s and a hard 20-req/day free-tier quota during live verification; the lite tier was live-tested against this exact prompt/schema and found more reliable, not just higher-quota.

**Never:** Do not build the Add Photo path (Story 2.2), the polished in-progress/failure UI (Story 2.3), or the Entries list display (Story 2.4) — this story's dialog only needs to close/confirm on success. Do not add the `classification` column (Epic 3's Story 3.1 owns that `ALTER TABLE`). The `EstimationProvider` input type only needs to cover text for now — Story 2.2 will broaden it to include photo input; don't invent a photo input shape speculatively.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Happy path | Well-detailed description (e.g. "one double cheeseburger and medium fries with a can of diet soda"), submitted | `estimate()` returns `{ ok: true, description, calories }`; a new `entries` row is created (`input_mode='text'`); the dialog shows the returned calorie count and closes | N/A |
| Insufficient detail | Vague description (e.g. "some food") | `estimate()` returns `{ ok: false, reason: 'insufficient_detail' }`; no `entries` row created; dialog shows a plain retry message, original text stays editable | N/A |
| Hard estimation failure | Gemini call throws (network drop, API error) | No `entries` row created; dialog shows a plain "the attempt failed, try again" message, original text preserved | Caught in the route, returns `{ error: { code: 'estimation_failed', message } }`, 500 |
| Empty submission | Blank/whitespace-only description | No call made | Inline validation error, no request sent |

## Code Map

- `lib/db/schema.ts` -- add `entries` table: `id` (uuid, default `gen_random_uuid()`, PK), `userId` (uuid FK → `auth.users`, cascade), `inputMode` (text, `'text'`/`'photo'`), `descriptionText` (text), `calories` (integer), `createdAt` (timestamptz, default now) — no `classification` column yet (Epic 3 adds it)
- `drizzle/` -- new migration for `entries`, generated via `npx drizzle-kit generate`, reviewed before applying (Story 1.1 precedent: drizzle-kit may try to re-touch the `auth.users` stub — strip any such statement before running)
- `lib/estimation/types.ts` (new) -- `EstimationProvider` interface: `estimate(input: { mode: 'text'; description: string }): Promise<{ ok: true; description: string; calories: number } | { ok: false; reason: 'insufficient_detail' }>`
- `lib/estimation/gemini-adapter.ts` (new) -- `GeminiAdapter implements EstimationProvider`. Calls `https://generativelanguage.googleapis.com/v1beta/models/gemini-flash-lite-latest:generateContent` via `fetch()` (no SDK dependency — matches this codebase's existing minimal-dependency pattern), `GEMINI_API_KEY` from env (server-only, guard-checked like every other env var in this codebase), `thinkingConfig: { thinkingLevel: "LOW" }`, structured JSON output via `responseSchema` (`sufficient_detail: boolean`, `description: string`, `calories: integer`) so the model's own judgment on detail-sufficiency drives the `ok`/insufficient-detail branch — never a client-side heuristic. A non-2xx response or thrown fetch error propagates as a real exception (per AD-2, this is the "hard failure" path, distinct from the model's own `sufficient_detail: false`).
- `lib/services/entries.ts` (new) -- `createEntry(userId, inputMode, descriptionText, calories)`, sole writer to `entries` (AD-1)
- `app/api/entries/route.ts` (new) -- `POST` handler: `export const maxDuration = 60`; resolve user via `lib/supabase/server.ts` (401 if absent); validate non-empty `descriptionText`; call `GeminiAdapter.estimate()`; on `ok: true`, call `createEntry()` and return `{ ok: true, calories }`; on `ok: false`, return `{ ok: false, reason: 'insufficient_detail' }` (200 — an expected outcome, not an error); on thrown error, log server-side and return `{ error: { code: 'estimation_failed', message } }` (500)
- `components/ui/dialog.tsx` (new, via `npx shadcn@latest add dialog`) -- DESIGN.md explicitly inherits shadcn's unmodified default styling for `Dialog`; no restyling needed (unlike `input.tsx`/`button.tsx`/`radio-group.tsx`)
- `app/log-entry-dialog.tsx` (new) -- client component: textarea + submit, opened by the "Add Text" button. States: idle (input) → submitting (bare "Estimating…" text, no polish) → success (shows returned calories, auto-closes) | insufficient-detail (plain retry message, textarea re-enabled with original text intact) | hard-failure (plain "attempt failed, try again" message, same textarea preserved)
- `app/page.tsx` (existing, Epic 0 placeholder) -- wire the existing "Add Text" `Button` to open `LogEntryDialog`; "Add Photo" stays inert (Story 2.2)

## Implementation Notes

- `lib/estimation/types.ts` / `gemini-adapter.ts`: `GeminiAdapter` calls `https://generativelanguage.googleapis.com/v1beta/models/gemini-flash-lite-latest:generateContent` directly via `fetch()` (no SDK), `x-goog-api-key` header, `thinkingConfig: { thinkingLevel: "LOW" }`, and a `responseSchema` requesting `sufficient_detail`/`description`/`calories`. The model's own `sufficient_detail` judgment drives the `ok`/insufficient-detail branch; only a genuine call failure (non-2xx, missing content, unparseable JSON, or a structurally/semantically invalid payload — see review below) throws.
- `lib/services/entries.ts`: `createEntry()`, the sole writer to `entries` (AD-1) — confirmed via repo-wide grep that no other code path touches the table.
- `app/api/entries/route.ts`: `maxDuration = 60` is a genuine Next.js route segment config export (not a comment) — confirmed present in the production build output (`/api/entries` listed as a dynamic `ƒ` route).
- `app/log-entry-dialog.tsx`: shadcn's `Dialog` installed unmodified per DESIGN.md. Five states (idle/submitting/success/insufficient_detail/error) as scoped — no attempt at Story 2.3's polish.
- **Model changed mid-story: AD-2 amended from `gemini-3.8-flash` to `gemini-3.5-flash-lite`.** The originally-planned full-tier free key hit both persistent `503` ("high demand") errors and a hard 20-`generate_content`-requests/day quota (confirmed via the API's own structured `RESOURCE_EXHAUSTED` error: `quotaId: GenerateRequestsPerDayPerProjectPerModel-FreeTier`, `quotaValue: 20`) — genuine evidence the request itself was well-formed (a malformed request 400s instead), purely an external capacity/quota ceiling. Rather than wait for the daily reset, the human asked whether `gemini-2.5-flash-lite` (deprecated; current equivalent `gemini-3.5-flash-lite`, reached via the `gemini-flash-lite-latest` alias, same alias-not-pinned-name pattern as the full tier) would work for text estimation, image recognition, and classification. Live-tested directly against the actual prompt/schema before switching: correct calorie estimate (1,050 kcal for the exact happy-path example below), correct insufficient-detail judgment, and confirmed multimodal image support via a synthetic test image (for Story 2.2) — with zero `503`s across every test call, more reliable than the full tier, not just higher-quota. The human chose to switch permanently rather than treat it as a temporary workaround; `ARCHITECTURE-SPINE.md`'s AD-2, Tech Stack table, and Structural Seed diagram were all updated, and the decision logged to the architecture's `.memlog.md`.
- **Full live verification completed after the model switch**, closing the two AC bullets this story was blocked on: happy path (well-detailed description → real `entries` row created, correct calorie count shown, dialog auto-closes) and insufficient detail (vague description → no `entries` row, plain retry message, text preserved) were both re-run through the actual browser UI against the real local Supabase instance and the real (now-working) Gemini API.
- Everything else was live-verified earlier and re-confirmed unaffected by the model swap (the swap only changes `GEMINI_MODEL_ENDPOINT`, not any surrounding logic): empty submission (client validation, no network call); the hard-failure path (real `503`/`429` responses against the old model, caught and mapped to the spec's exact "the attempt failed, try again" copy, confirmed zero `entries` rows written); server-side length rejection via a direct API call bypassing the client's `maxLength`; the dialog-close-mid-flight abort/staleness fix (see Review Triage Log) confirmed via a genuine submit→close→reopen→resubmit sequence.

## Review Triage Log

Three reviewers ran (Blind Hunter, Edge Case Hunter, Verification Gap). Several converged on the same root causes; grouped below by cause, not by reviewer.

- **[high, patch]** Closing the Log Entry dialog while a submission was still in flight didn't cancel or ignore that request — its eventual response could arrive after the dialog was reopened and a *different* submission was already running, silently overwriting that second submission's in-progress/result state with the first (abandoned) one's outcome, or auto-closing the dialog out from under an unrelated later submission. Flagged by both Edge Case Hunter (with a concrete repro: submit A, close, reopen, submit B, A's late response clobbers B's state) and Blind Hunter. Fixed: added a `requestIdRef` incremented on every new submit attempt and on close, checked before every post-`await` `setState` call, plus an `AbortController` that actually cancels the stale network request rather than merely ignoring its result. Live-verified: submit→close→reopen→submit-different-text→wait for response shows only the second submission's own outcome, with the textarea correctly holding the second description throughout.
- **[high, patch]** `GeminiAdapter.estimate()` trusted the parsed JSON payload's shape and values with no runtime validation beyond `JSON.parse` succeeding — a missing `calories` field produced `NaN` (surfacing three layers downstream as an opaque DB-insert 500 with no diagnostic value), a missing `sufficient_detail` key silently evaluated as falsy and was misread as a legitimate "insufficient detail" judgment with zero logging, and neither the schema nor the code bounded `calories` to a sane non-negative range or required a non-empty `description` on the success branch. Flagged independently by all three reviewers, converging on the same root cause from different angles. Fixed: added `isValidPayload()`, validating `sufficient_detail` is genuinely boolean, and (on the true branch) that `description` is a non-empty string and `calories` is a finite number within `[0, 20_000]`; anything that fails this check now throws a real, loggable error instead of silently degrading.
- **[medium, patch]** The user's free-text description was spliced directly between `"""` prompt delimiters with no escaping, so a description containing its own `"""` sequence could attempt to break out of the "quoted user data" framing and append instructions of its own (e.g. forcing `sufficient_detail: true` and an arbitrary `calories` value). Flagged by Blind Hunter. Fixed as defense-in-depth: `"""` sequences in the description are replaced with `'''` before interpolation. The payload-validation fix above is the real backstop regardless (any resulting bad output still has to pass `isValidPayload`'s bounds check).
- **[medium, patch]** No length limit on the submitted description, client or server. Flagged by both Blind Hunter and Edge Case Hunter as a cost/DoS vector (unbounded text forwarded verbatim into the Gemini prompt) and a data-quality gap (unbounded `text` column). Fixed: added `MAX_DESCRIPTION_LENGTH = 2000` to `lib/constants.ts`, enforced via `maxLength` on the textarea and an explicit server-side check in the route. Live-verified: a direct 2,500-character API call (bypassing the client) is rejected with `400 invalid_input`.
- **[low, patch]** Resubmitting with blank text after a prior hard-failure error left the stale "the attempt failed, try again." message on screen at the same time as the new blank-field validation message — two contradictory status lines, and the screen-reader-only `aria-describedby` pointed at just one of them. Flagged by Edge Case Hunter. Fixed: the blank-text early-return now also clears `message`/resets `status` before setting the validation flag. Live-verified: resubmitting blank text now shows only the validation message.
- **[low, patch]** The `entries` table had no index on `user_id`/`created_at`, even though every Day-scoped query this epic and Epic 3 need (Story 2.4's list, budget/trends reads) filters and orders by exactly those columns. Flagged by Blind Hunter. Fixed while the table was still empty: added a composite index via a new migration (`drizzle/0002_vengeful_tomas.sql`), applied and confirmed present (`\di entries*`) against the live local instance.
- **[low, false]** `lib/services/entries.ts` appeared "missing from the diff" to two reviewers (Blind Hunter, Verification Gap), who flagged it as a build-breaking omission. Verified as a review-tooling artifact, not a code defect: the file was genuinely on disk and correct, just not included in the `git add -N` intent-add list used to generate the diff shown to reviewers. No code change needed; the diff-generation step was corrected for review purposes.
- **[low, false]** The API route's `401 unauthenticated` branch was flagged (Blind Hunter) as reachable in a way that would show an inline error instead of redirecting to `/login`, diverging from `preferences-form.tsx`'s established pattern. Edge Case Hunter independently checked and disproved the underlying concern: `proxy.ts`'s matcher already covers `/api/entries` (only `/login`, `/register`, `/api/auth/*` are excluded), so this branch is defensive-only, unreachable in normal operation — the same disposition already accepted for the identical pattern in Story 1.3's review.
- **[low, false]** Spec Tasks/AC checklist showing items unchecked while the code was already functionally complete. Verified as the expected mid-workflow state (same as Story 1.4's identical false finding) — resolved by this Finalize pass itself.
- **[low, deferred]** The submit-guard against a double-submit race is state-based (`if (status === "submitting") return`) rather than a synchronous ref. Flagged by Blind Hunter with hedged confidence; Edge Case Hunter independently reviewed the same concern and downgraded it, noting the textarea can't submit via Enter (multiline) and React's render timing makes two genuinely concurrent clicks unlikely in practice. Deferred: narrow, low real-world risk, matching the disposition given to the identical finding in Story 1.2. Logged in `deferred-work.md`.
- **[low, deferred]** The new `entries` table has `isRLSEnabled: false`, relying entirely on the service-layer (AD-1) for per-user access control with no DB-level backstop. Flagged by Blind Hunter. Deferred: this mirrors the pre-existing, already-accepted pattern on `profiles` — not a gap introduced by this story specifically, and closing it (enabling RLS with a per-user policy) is a security-hardening decision better made once across all tables than piecemeal per story. Logged in `deferred-work.md`.
