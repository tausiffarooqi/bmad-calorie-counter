## Intent

**Problem:** Nothing distinguishes a user's first app-open of a new Day from any later visit — the Daily view always renders the same way, with no proactive check-in and no persisted signal for "have they already seen today's greeting."

**Approach:** Add a nullable `lastFirstLoginPromptAt` timestamp to `profiles`. On each Daily view load, the service layer checks whether that timestamp already falls within the current Day (`dayBoundary()`) — if not, it's the first open of the Day: mark it shown (update the timestamp) and tell the client to render the First-Login prompt (a Prompt-card asking "Log a meal now?" alongside the fresh Remaining Calorie Budget) instead of the normal Daily view, until the user resolves it.

## Boundaries & Constraints

**Always:** "First open of the Day" is derived by comparing `lastFirstLoginPromptAt` against `dayBoundary(now, tz).start` — the same Day-boundary function every other Day-scoped check already uses, never separate date math. Marking the prompt shown happens server-side, at the moment the Daily view is loaded/queried — not when the user later taps a button — so a second app-open the same Day never re-prompts even if the user closes the tab without responding. Both "Log a meal" and "Not now" resolve to the same next state: the normal Daily view, fully rendered with its usual Recommendation cards/Over-Target banner — resolving is a client-side-only state change (the server already marked it shown at load time, no second round-trip needed). The prompt shows the same `remainingBudget` value the Daily view already computes — no separate budget calculation. The prompt only renders when today's Entries list is also empty (`entries.length === 0`, from the same response) — if Entries already exist for today (e.g. logged from another device/tab before this one's first visit that day), the normal Daily view renders instead, never hiding already-logged Entries behind the prompt.

**Never:** Do not add the tone-adaptive "yesterday" message or greeting text (Story 4.2's own, separate scope) — this story's prompt card shows only the budget and the log-a-meal question. Do not add the breakfast-offer card (Story 4.4). Do not persist any "did they accept or decline" outcome — only whether the prompt was shown. Do not add a client-side (localStorage) fallback for "already shown today" — the server-side timestamp is the single source of truth. Tapping "Log a meal now?" does not auto-open either logging dialog (human decision) — it only dismisses the prompt and reveals the Daily view's Add Photo/Add Text buttons, same as "Not now"; the two buttons differ only in copy/engagement framing, not in what renders next.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| First app-open of a new Day | `lastFirstLoginPromptAt` is `null`, or falls before today's Day-start | Daily view load marks it shown (updates the timestamp) and returns `showFirstLoginPrompt: true` | N/A |
| Second (or later) app-open, same Day | `lastFirstLoginPromptAt` already falls within today's Day window | `showFirstLoginPrompt: false` — lands directly on the normal Daily view | N/A |
| Very first login ever (right after registration) | `lastFirstLoginPromptAt` is `null` (column default) | Same as "first open of a new Day" — prompt shows | N/A |
| User taps "Log a meal now?" or "Not now" | Either button | Prompt dismisses client-side; normal Daily view renders underneath, unchanged either way | N/A |
| First open of the Day, but Entries already exist for today | `showFirstLoginPrompt: true` from the server, but `entries.length > 0` | Normal Daily view renders (not the prompt) — already-logged Entries are never hidden | N/A |

## Implementation Notes

- `lib/db/schema.ts`: added `lastFirstLoginPromptAt` (nullable `timestamp with time zone`, no default) to `profiles`, exactly as the Code Map specified. Migration generated via `npx drizzle-kit generate` (`drizzle/0004_regular_snowbird.sql`, a single `ALTER TABLE ... ADD COLUMN`); applied directly against the local Supabase Postgres via `psql` (drizzle-kit's own `migrate`/`push` path was not attempted this session — the established `psql` workaround was used straight away per the Code Map note) and confirmed via `information_schema.columns`.
- `lib/services/profiles.ts`: `checkAndMarkFirstLoginPrompt(userId, tz)` reads the profile via the existing `getProfile()`, compares `lastFirstLoginPromptAt` against `dayBoundary(new Date(), tz).start` (the same function/instance every other Day-scoped check in the app uses — no inline date math), and only issues an `UPDATE` when the prompt hasn't been shown yet today. A missing profile row (data-corruption case, mirrors the route's own guard) returns `false` rather than throwing. This is a plain read-then-write, not a CAS, matching the spec's explicit acceptance of that at this app's scale.
- `app/api/entries/route.ts`: `GET` now calls `checkAndMarkFirstLoginPrompt(user.id, tz)` concurrently with the existing `getEntriesForDay`/`getProfile` reads (`Promise.all`), and includes `showFirstLoginPrompt` in the JSON response. Deliberately given its own `.catch()` that logs and falls back to `false` rather than rethrowing — a failure in this enrichment signal must never take down the whole Daily view load (same reasoning `POST`'s own post-submission enrichment step already uses in this file).
- `hooks/use-daily-view.ts`: added a `showFirstLoginPrompt` state field, defaulted to `false`, populated from the response the same way `remainingBudget`/`recommendations` already are.
- `app/first-login-prompt.tsx` (new): a Prompt-card matching DESIGN.md's spec (`bg-card`/`border-border`/`rounded-md`) and the mockup's own copy shape (`mockups/daily-view.html`'s `.prompt-card`) — "Remaining budget today: **N calories**. - `app/page.tsx`: added local `promptDismissed` state and a derived `showPrompt = budgetReady && showFirstLoginPrompt && !promptDismissed` gate. ## Spec Change Log

- **Finding:** Blind Hunter flagged that the prompt shows unconditionally on the day's first load, even if Entries already exist for today (e.g. logged from another device/tab before this one's first visit that day) — those Entries would be temporarily hidden behind the prompt until dismissed.
- **Amended:** Added an `entries.length === 0` condition to `## Boundaries & Constraints` (Always) and a new I/O & Edge-Case Matrix row.
- **Known-bad state avoided:** A user's already-logged Entries silently disappearing behind a prompt on a second device/tab's first visit that day, with no indication anything was hidden.
- **User decision:** Presented as a checkpoint (per the review process's intent-gap loopback) rather than amended unilaterally, since the gap was in the frozen Approach's own stated design. User chose to add the guard now as a small, penalty-free patch.
- **KEEP:** Everything else in the existing implementation (`checkAndMarkFirstLoginPrompt`'s day-boundary logic, the `lastFirstLoginPromptAt` schema/migration, `FirstLoginPrompt`'s own rendering, the client-side `promptDismissed` state) is correct and unaffected — only the render-gating condition in `app/page.tsx` needs the additional `entries.length === 0` check.
