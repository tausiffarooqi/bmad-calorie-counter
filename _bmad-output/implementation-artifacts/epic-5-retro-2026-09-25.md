## Findings

Three lenses ran against the diff, told what each story's own review already fixed so they wouldn't re-report it. Two things converged across every reviewer in both the original build-time review *and* this fresh retrospective pass — worth flagging with more weight than a routine deferral, even though neither is technically new.

### Already known, but now confirmed by every reviewer across two independent passes

- **The aggregate "X% of days within target" stat retroactively reclassifies history whenever the user changes their Daily Calorie Target.** `computeTrendDays()`/`computeTrendSummaryStats()` apply the *current* `dailyCalorieTarget` uniformly to every historical day (Story 5.1's own accepted "no historized target" simplification). Story 5.2 turns that per-row cosmetic simplification into a single trusted headline number: a user who lowers their target from 2500 to 1800 would see their 3-month compliance rate collapse instantly, with nothing about their actual eating having changed. I found and deferred this exact amplification during Story 5.2's own build review; Adversarial and Edge-Case Hunter both independently rediscovered it in this retrospective pass. Three independent findings across two review rounds on the same root cause is a stronger signal than a typical single-reviewer defer.
- **Two adjacent `aria-live="polite"` regions (the stats block and the day list) populate at the exact same instant on first load.** Also already found and partially disputed/deferred during Story 5.2's own build review (aria-live announcing the first reveal of async content is legitimate; the *simultaneous double announcement* is the real, narrower concern). All three lenses in this retrospective independently rediscovered it too.

### Real, verified — new this retrospective

- **A single-day trend window shows the identical date twice in the range label.** `app/(routes)/trends/page.tsx`: `{formatDayLabel(days[days.length - 1].dayStart)} – {formatDayLabel(days[0].dayStart)}` — when `days.length === 1`, both indices resolve to the same element, rendering e.g. "Mon, Jan 5 – Mon, Jan 5". A very plausible state for any new or lightly-active account. Verified directly. (Adversarial and Edge-Case Hunter, independently converged.)
- **The range label's correctness depends entirely on array-position semantics that cross a file/story boundary, with no explicit contract enforcing it.** `days[0]` is "most recent" and `days[days.length-1]` is "earliest" only because `computeTrendDays()`'s sort order says so — a fact recorded only in a code comment, not a type or shared constant. If Story 5.1's own sort direction ever changes for its own reasons, the label would silently invert with nothing failing (no test exists at the page layer at all, confirmed — `package.json`'s test script structurally cannot reach anything under `app/`). (Adversarial and Verification Gap, independently converged.)
- **The range label reads in the opposite direction from the day list directly below it.** The label goes earliest → latest (left to right); the list goes most-recent-first, oldest-last (top to bottom) — the same data, presented in opposite orders, on two adjacent UI elements. Real comprehension friction, only visible once both stories' pieces are viewed together. (Adversarial.)
- **A 3-month window spanning a calendar-year boundary would show a range like "Dec 28 – Feb 3" with no year on either end**, ambiguous which year each date belongs to. `formatDayLabel()` never includes a year. Verified directly — real, but **not yet reachable**: this project's entire history starts in September 2026, so the earliest a real 3-month window could span a year boundary is around January 2027. (Edge-Case Hunter.)
- **The stats block and day list are gated by two independently hand-written boolean expressions** (`!firstLoadPending && !loadError && stats && days && days.length > 0` vs. the same without `stats`) rather than one shared guard, even though the epic's own cross-story rule ("no stats block at all when the window is empty") depends on them never disagreeing. Currently harmless — both conditions are identical in practice — but a future edit to only one could silently violate the rule with nothing catching it. (Verification Gap.)

### Real but low-impact — logged, not actioned this round

- `getEntriesForDay()` — named and originally scoped for a single Day's entries — is now reused unmodified for a 3-month range, with no rename or doc update noting the broadened usage. No behavioral issue today; a future change made under the old single-day assumption could silently affect this epic.
- `computeTrendSummaryStats()`'s own defensive empty-array branch is dead code in production, since the one real call site (`page.tsx`) already guards `days.length > 0` before ever calling it — the actual "no stats when empty" invariant lives entirely in the page's conditional, not in the function whose own doc comment implies it owns that guarantee.
- `computeTrendSummaryStats(days)` is invoked directly in the render body, unmemoized — recomputes its full reduce over the whole window on every unrelated re-render. Trivial at this data scale (≤90 rows).
- No component/page-level test exists for `app/(routes)/trends/page.tsx` — the same well-established, repeatedly-confirmed project-wide gap.

## Action items

1. **Fix the date-range label as one piece of work**: derive earliest/latest by value (e.g. `reduce` over `dayStart`, or an explicit `{earliest, latest}` return from the trends service) instead of positional indexing, special-case a single-day window to show one date instead of a duplicated range, and reorder or annotate it to match the day list's own most-recent-first direction instead of silently conflicting with it. Owner: next dev session.
2. **Add year disambiguation to `formatDayLabel()`** when the displayed range spans a calendar-year boundary. Low urgency (not yet reachable), but cheap to bundle with item 1 while that code is already being touched. Owner: next dev session.
3. **Extract one shared boolean** (e.g. `hasData`) for the stats-block/day-list visibility gate instead of two independently-written, currently-identical conditions, so the epic's "no stats when empty" rule is structurally guaranteed rather than coincidentally true. Owner: next dev session.
4. **Re-weight the two carried-over findings (target-reclassifies-history, dual aria-live) given they've now been independently rediscovered by every reviewer across two separate review rounds.** Neither is new, but the convergence is a stronger signal than a typical single-pass defer — worth prioritizing over other similarly-tiered deferred items when accessibility/UX polish work is next picked up. Owner: human decision on priority.
