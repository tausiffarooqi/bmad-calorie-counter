## Findings

Three lenses (Adversarial, Edge-Case Hunter, Verification Gap) ran against the diff, explicitly weighting the seam between Stories 0.1 and 0.2. I additionally ran an epic-scoped architecture-delta check myself: since Epic 0's entire purpose is "every later screen inherits this," I checked whether that promise actually held across all five epics built since, not just at the two stories' own review time.

### Real, verified — the foundation didn't fully hold

- **`DialogContent` has no visible keyboard-focus indicator** (`components/ui/dialog.tsx:64`). Verification Gap and Edge-Case Hunter independently found the same mechanism: Story 0.2's new global `:focus-visible` rule lives in `@layer base`, but Tailwind v4's own layer order (`@layer theme, base, components, utilities`) means the `utilities`-layer `outline-none` class — which `DialogContent`'s `className` carries unconditionally — always wins regardless of specificity or focus state. I confirmed this by reading `dialog.tsx:64` directly: `outline-none` with no `focus-visible:ring-*` anywhere in the file. `Button`/`Input`/`RadioGroupItem` are **not** actually broken by the same mechanism (Edge-Case Hunter's report overstated this for `Button`) — each of those already pairs its own `outline-none` with its own `focus-visible:ring-3 focus-visible:ring-ring/50` (verified: `ring-ring` resolves to the same clay `--ring` color), so they show a working clay indicator via box-shadow-style `ring-*`, just not via the mechanism Story 0.2 added. `DialogContent` has no such fallback at all, so a keyboard user tabbing (or Radix auto-focusing) into any dialog — `LogEntryDialog`, `LogPhotoDialog`, every modal in the app — sees **zero** focus indicator. This directly contradicts Story 0.2's own stated Intent ("every focusable element — not just components that opt in explicitly — renders the clay ring"). No CSS/UI test exists anywhere in this project to catch it (only `node --test lib/**/*.test.ts`), and Story 0.2's own manual verification exercised a plain `<a>` deliberately built *without* `outline-none` — so this exact interaction was never checked, then or since.
- **A dead demo link ships on the real, production Daily view.** `app/page.tsx:275-277`: `<a href="#" ...>Log in</a>`, added by Story 0.2 specifically to prove the new focus rule works on a non-shadcn element, on what was then a temporary foundation-showcase page. That showcase page was fully replaced by the real Daily view starting Epic 3 — but this one element survived, unconditionally, and now renders at the bottom of every authenticated user's Daily view. It does nothing (`href="#"`, no handler); Edge-Case Hunter additionally noted it has no `preventDefault`, so activating it mutates the URL hash. No single later story's own review ever flagged this, because none of their diffs touched this line — it was never *part of* any subsequent change, just leftover scaffolding nobody was looking at. Exactly the class of defect this retrospective exists to catch.
- **UX-DR27 ("at most one primary + one secondary action, never more than two competing actions on a single surface") is violated by the combination of two later stories.** Story 4.1's `FirstLoginPrompt` (1 primary + 1 secondary button) and Story 4.4's `BreakfastOfferCard` (2 more secondary/outline buttons) can render simultaneously — confirmed by reading `app/page.tsx`'s current `showPrompt` branch: both cards are gated on independent conditions (`showFirstLoginPrompt && entries.length===0`, and `showBreakfastOffer` requiring the same plus before-10am/not-yet-accepted/not-over-target) that are not mutually exclusive. On a real first-login-before-10am session, up to 4 buttons (1 primary, 3 secondary-styled) can be on screen at once. Story 4.4's own review (already committed) checked this combination against Story 4.1's *decline behavior* but never against Epic 0's cross-cutting action-count rule, since that rule lived outside either story's own spec scope.

### Verified false or already-explained — reported but not carried forward

- Dark-mode `--ring` was never re-themed to clay (`app/globals.css:125`, still shadcn's stock `oklch(0.556 0 0)`) — confirmed real, but confirmed **currently inert**: nothing anywhere in the app (`app/`, `components/`, `lib/`) ever applies the `.dark` class or exposes a theme toggle. Zero current user impact; would only matter if dark mode is ever wired up. Not carried forward as an action item, logged as a defer below.
- `--text-sm` comment claims Tailwind's default line-height is "14px/1.5" — checked directly against `node_modules/tailwindcss/theme.css:349-350`: the actual default is `1.25rem / 0.875rem ≈ 1.43`. The comment is factually wrong, but the **code** has no bug (body text still renders at Tailwind's real default either way, since no override was written) — a documentation-accuracy nit, not a rendering defect.
- Adversarial's findings about the button-radius fix and the TypeScript version pin "lacking inline comments/story attribution" are real observations about the diff in isolation, but both decisions are already fully explained in `spec-0-1-design-tokens-visual-foundation.md`'s own frozen Decision block and Review Triage Log (written at the time, not reconstructed now) — the paper trail exists, just not duplicated as inline code comments. No further action.
- Edge-Case Hunter's compound-typography-token concern (whether Tailwind v4 actually recognizes `--font-weight`/`--letter-spacing` companions on a `text-*` token) and the button-radius-regression concern were both investigated and confirmed as non-issues by Edge-Case Hunter itself, against the real Tailwind engine source and the component's own base class — correctly not carried forward as findings.

### Real but low-impact — logged, not actioned this round

- `--text-label`/`--text-display-number`/`--text-recommendation` use fixed `px` values rather than `rem`, so they don't scale with a user's OS/browser font-size *preference* (distinct from page zoom, which still works regardless of unit) — a genuine, if narrow, accessibility gap Edge-Case Hunter identified correctly.
- `--text-label` has no baked-in `text-transform: uppercase`, so every consumer must remember to pair it with the `uppercase` utility separately (both current call sites do; nothing enforces it for a future one).
- `--text-display-number`'s fixed `52px` has no responsive/clamp sizing for narrow viewports — plausible, but unverified: the containing element is `max-w-sm` (384px), which comfortably fits any calorie figure this app actually produces. Recorded as an open question (needs an actual narrow-viewport check), not asserted as a confirmed defect.
- The implicit `outline-none`-requires-its-own-`focus-visible:ring-*` contract between Story 0.2's global rule and every shadcn-derived component is undocumented anywhere (DESIGN.md/AGENTS.md) — worth stating explicitly once the `DialogContent` fix above lands, so the next new interactive primitive doesn't repeat the same gap.
- `app/globals.css` has no trailing newline at EOF — already logged in `deferred-work.md` from Story 0.2's own original review; not re-logged here.

## Action items

1. **Fix `DialogContent`'s missing focus-visible indicator.** `components/ui/dialog.tsx:64` — add a `focus-visible:ring-*` fallback matching `Button`/`Input`/`RadioGroupItem`'s existing pattern (e.g. `focus-visible:ring-3 focus-visible:ring-ring/50`), so keyboard focus is visible inside every dialog. Owner: next dev session. *(Remediation — proposed, not applied.)*
2. **Remove the dead `<a href="#">Log in</a>` element.** `app/page.tsx:273-277` — Story 0.2 scaffolding that survived into the shipped, production Daily view across five subsequent epics; renders unconditionally, does nothing. Owner: next dev session. *(Remediation — proposed, not applied.)*
3. **Reconcile UX-DR27 against Stories 4.1 + 4.4's combined behavior.** `FirstLoginPrompt` and `BreakfastOfferCard` can render simultaneously, exceeding "at most one primary + one secondary action." This is a product/UX call (sequence the two cards? combine into one choice? relax the rule for this specific screen?), not something to resolve unilaterally — propose as a small follow-up story or an explicit, recorded exception to UX-DR27. Owner: human decision needed first.
4. **Document the `outline-none` / `focus-visible:ring-*` pairing requirement.** Once item 1 lands, add a line to DESIGN.md or AGENTS.md: any interactive primitive using the `outline-none` reset must supply its own `focus-visible:ring-*` styling, since the global base-layer rule cannot reach it. Owner: whoever picks up item 1.
5. **Process lesson:** no automated or scheduled check ever re-verifies that a foundation epic's cross-cutting rules still hold as later epics build on top of it — each story's own review only checks its diff against its own spec. All three real findings above went undetected for multiple epics because of this. Consider running a lightweight foundation-conformance spot-check earlier than "whenever someone finally runs the retrospective," rather than deferring every epic's retro to the very end of the project (all six were still `optional`/unrun until this session).

## Acceptance verdict

**Accepted-with-open-items.** Criteria profiled from the two stories' own ACs (no separate epic-level AC exists in epics.md). The core deliverables are demonstrably in place and held up well across all five subsequent epics: zero hardcoded hex colors anywhere in `app/`/`components/` outside comments, the radius scale (`sm`/`md`/`lg`) is used correctly and consistently (including the one `lg`-radius Recommendation card, exactly matching DESIGN.md), and the compound typography tokens (`text-label`/`text-display-number`/`text-recommendation`) added during Story 0.1's own review are still the ones later stories (e.g. Story 5.1's Trends page) reused rather than reinventing arbitrary values. Both stories are `done`, no story is unfinished. Against that, Story 0.2's own central, explicitly-stated claim — "every focusable element... renders the clay ring" — is verified false for `DialogContent`, and a piece of its own scaffolding (the dead demo link) is still live in production. Neither is severe enough to call the epic's foundation unusable (both are narrowly-scoped, cheaply fixable), but both are real, verified, currently-shipping gaps against the epic's own stated intent — hence open items, not silent acceptance.
