# Epic 2 Retrospective — Meal Logging & Estimation

## Epic summary

Epic 2 shipped the core meal-logging loop: submit an Entry by photo or text, get it estimated via Gemini, see in-progress/failure states, view the day's logged Entries, and have the in-progress state announced to assistive technology.

- **Stories:** 2.1 Log a Meal via Text (`ca3ca77`), 2.2 Log a Meal via Photo (`63bd222`), 2.3 In-Progress & Failure States (`bd9ff46`), 2.4 View Logged Entries (`ce217e4`), 2.5 Accessible In-Progress Announcement (`ec46083`). All `done`; `pending_stories` empty.
- **Diff range:** `0b20eb5..ec46083`, 5 non-merge commits, largest single-story diffs in the project so far (`app/api/entries/route.ts` alone gained 264 net lines in this epic).
- **Evidence inventory:** all five story specs read in full. Each already carries an unusually thorough Review Triage Log — several genuinely serious bugs were caught and fixed at implementation time (a stale-submission race that could clobber a second, unrelated submission's state; unvalidated Gemini JSON payloads producing silent `NaN`/false-negative failures; a prompt-injection vector via unescaped `"""` delimiters; an uncancelled pre-submit compression phase). Sprint status confirms all `done`. Session logs not available (predates this session).

## Previous-retro follow-through

Epic 0 and Epic 1's retrospectives logged 4 and 6 action items respectively, none belonging to Epic 2 — nothing to transition here. No evidence either epic's items have landed yet (no commits since either retro touch the affected files); recorded as "no evidence found," not "not done."

## Findings

Three lenses ran against the diff, told to focus on cross-story seams (a shared hook, a cross-file id contract, the write-path/read-path/day-boundary interaction) rather than re-finding what each story's own already-thorough review caught. I additionally checked whether Epic 2's own architectural rules (AD-4 no persistent photo storage, AD-9 explicit `maxDuration`, Story 2.4's "most-recent-last" ordering) still hold across every later epic.

### Real, verified — new findings this retrospective surfaced

- **Closing the client's dialog does not cancel the server-side write.** `hooks/use-entry-submission.ts`'s `AbortController` cancels the *client's* fetch, but `POST /api/entries` never reads or forwards the request's `AbortSignal` — confirmed directly: zero references to `signal`/`AbortController` anywhere in `app/api/entries/route.ts` or `lib/estimation/gemini-adapter.ts`. A user who closes the dialog mid-submission is told, and believes, they cancelled it — but `provider.estimate()` and `createEntry()` both run to completion server-side regardless, silently creating an Entry the user thought they'd stopped. (Adversarial, Edge-Case Hunter, and Verification Gap — all three independently, the most-converged finding of this retrospective.)
- **The Entries list reintroduces the exact live-region bug Story 2.5 was built to fix — just in a file Story 2.5's own frozen scope excluded.** `app/entries-list.tsx`: `if (entries.length === 0) return null;` gates the entire `<ul aria-live="polite">`. The very first Entry logged each Day transitions the component from rendering nothing to mounting the live-region node *with its content already set in the same commit* — the precise "freshly-mounted-with-text-already-set" failure mode `components/live-region.tsx`'s own design specifically works around for the dialogs. Story 2.5's own review flagged the general risk of a third, uncoordinated live region on the page and explicitly deferred it as out-of-scope (never mentions `entries-list.tsx`) — but that deferral was about *double-announcement*, not this more specific *first-entry-never-announced* mount-timing bug. Verified directly by reading the component. (Adversarial and Edge-Case Hunter, independently converged.)
- **Closing the dialog during the ~1.2s success-confirmation window silently drops the list refresh for an Entry that was already, definitely created.** `hooks/use-entry-submission.ts`'s `cancelAndReset()` — its own doc comment states it "cancels a pending success auto-close." This is correct/intentional for a genuinely in-flight submission, but `cancelAndReset()` runs unconditionally from `handleOpenChange(false)` regardless of whether `status` is `"submitting"` or already `"success"`. In the success case, the POST already resolved `ok: true` and `createEntry()` already ran — the write is durable — but clearing the pending timer also discards the `onSuccess?.()` callback that bumps `refreshKey`. The user closing a dialog that's already showing "Logged — about N calories" (arguably just dismissing a message, not cancelling anything) causes that Entry to not appear in the list until some unrelated later refresh happens. Verified directly by tracing `cancelAndReset()`'s own comment against `handleOpenChange`'s unconditional call to it. (Edge-Case Hunter.)
- **`MAX_DESCRIPTION_LENGTH`'s documented guarantee doesn't cover what's actually written to the DB.** `lib/constants.ts` documents the constant as bounding `entries.description_text`, and the route does check it — but only against `body.descriptionText` (the user-typed input on the text path). `createEntry()` is actually called with `result.description` — Gemini's own generated/cleaned restatement (text path) or entirely model-authored text (photo path, which has no user-typed input to bound at all) — which `isValidPayload()` only checks for non-empty, never for an upper bound. Verified directly: grepped every `createEntry(` call site and every `MAX_DESCRIPTION_LENGTH` reference. (Adversarial and Edge-Case Hunter, independently converged.)
- **The same "route's own defense-in-depth 401 shows an inline error instead of redirecting" pattern Epic 1's retrospective found in `/api/preferences` is confirmed again in `/api/entries`.** `GET /api/entries`'s unauthenticated branch returns a JSON 401; `entries-list.tsx`'s own fetch only redirects to `/login` when `response.redirected` (the proxy-triggered path), the same asymmetry already logged for Preferences. Two independent occurrences of the identical class of gap strengthens the case for one shared client-side fix rather than two separate patches. (Adversarial; cross-referenced with the Epic 1 retro.)

### Real but low-impact — logged, not actioned this round

- The photo dialog's insufficient-detail message reuses the text dialog's "add a bit more detail" copy verbatim, which reads oddly for a blurry/unclear photo (a "retake/choose a clearer photo" framing would fit better). Cosmetic copy nit.
- `aria-describedby="photo-only-notice"` is an implicit, string-matched id contract split across `log-photo-dialog.tsx` and `page.tsx` — fragile to a future refactor, currently working.
- A narrow 5am-boundary race: logging in roughly the last 1-2 seconds before the Day boundary rolls over can make the entry briefly "vanish" from the freshly-recomputed "today" list. Extremely narrow timing window, no observed real-world occurrence.
- A DB-insert failure after a successful (already-billed) Gemini call has no retry/cache — a user-initiated retry re-pays for a fresh Gemini call instead of reusing the already-computed estimate. Worth designing properly later (server-side cache keyed by request), not a one-line fix — converges with the same "cheap retry path" idea already logged from Story 3.1's own deferred item.
- `entries-list.tsx` uses a plain `cancelled` boolean rather than an `AbortController` for stale-response handling, unlike the dialogs' stronger mechanism. Already verified functionally correct by Story 2.4's own review ("always correctly ignored regardless of resolve order") — a consistency preference, not a bug.
- Inconsistent recovery-message wording across the epic's five stories ("try again" / "try reloading" / "try another photo"). Cosmetic.
- `app/api/entries/route.ts` is now 582 lines handling concerns from three different epics (entry creation, budget, recommendations, first-login prompt, tone message, breakfast offer) — a god-file candidate. Noted for awareness, but most of this growth happened in Epics 3-4, not Epic 2 itself (which added 264 of the 582 lines); better addressed when retrospecting whichever epic pushed it past a reasonable size, not attributed to this one.
- The "multiple independent `aria-live` regions can race/conflict" concern has now been independently rediscovered and separately deferred across **five** different stories since it first surfaced here (2.4/2.5, then 3.2/3.3/3.5, 4.3, and 5.1's own retrospective-adjacent review) without ever being consolidated into one fix. See Action Items — this is the strongest case in the project so far for finally doing the holistic pass every one of those five deferrals has been pointing at.

## Action items

1. **Make the server respect a cancelled/aborted submission.** `app/api/entries/route.ts`'s `POST` handler — read the incoming `Request`'s `signal`, forward it into `GeminiAdapter.estimate()`'s own `fetch()` call, and check `signal.aborted` before `createEntry()` runs. Owner: next dev session.
2. **Fix the first-Entry-of-the-day live-region mount bug.** `app/entries-list.tsx` — render the `<ul aria-live="polite">` wrapper unconditionally (vary only its children on `entries.length === 0`), matching the always-mounted pattern `components/live-region.tsx` already established for exactly this failure mode. Owner: next dev session.
3. **Make closing the dialog during the success-confirmation window still refresh the list.** `hooks/use-entry-submission.ts`'s `cancelAndReset()` / `handleOpenChange` — when `status === "success"` at close time, still invoke the `onSuccess?.()` callback (the write already happened; only the auto-close *timer* should be skipped, not the refresh it would have triggered). Owner: next dev session.
4. **Cap `result.description` before `createEntry()`.** `app/api/entries/route.ts` — truncate or reject `result.description` against `MAX_DESCRIPTION_LENGTH` before persisting, so the documented guarantee actually covers what's written (both the text-path's Gemini-cleaned restatement and the photo-path's fully model-generated description). Owner: next dev session.
5. **Consolidate the two now-confirmed "defense-in-depth 401 shows inline error, not redirect" occurrences** (`/api/preferences` from the Epic 1 retro, `/api/entries` from this one) into one shared client-side handling pattern rather than two separate patches. Owner: next dev session.
6. **Process lesson: finally do the holistic Daily-view live-region pass.** Five separate deferred-work.md entries across five different stories (2.4/2.5, 3.2/3.3/3.5, 4.3, 5.1) have each independently rediscovered and re-deferred some version of "multiple/uncoordinated `aria-live` regions on one page." Every one of those deferrals explicitly said "revisit as one holistic strategy, not per-element patches" — none has. Owner: human decision on priority, then a dedicated small story.

## Acceptance verdict

**Accepted-with-open-items.** Criteria profiled from the five stories' own ACs (no separate Epic-2-level AC in epics.md). All five stories `done`, `pending_stories` empty. The epic's core promise — submit by photo or text, get an estimate, see it persist, view it in a list, hear it announced — works, and each story's own review already caught and fixed several genuinely serious bugs before this retrospective ran (the stale-submission-clobber race, unvalidated Gemini payloads, the prompt-injection vector). Architectural rules established here (AD-4 no persistent photo storage, AD-9's explicit `maxDuration`) were directly re-verified and still hold cleanly across every later epic. Set against that: the client-side "cancel" not actually cancelling the server-side write is a real, user-trust-relevant gap, and the two live-region/refresh-timing bugs are genuine, if narrow, correctness issues — real and open, not silently accepted.

- Is the god-file growth of `app/api/entries/route.ts` (582 lines) worth a dedicated refactor story, or is it acceptable for a hobby-scale MVP at this size? A question better answered once Epic 3/4's own retrospectives are done and the full growth picture is visible.
