## Findings

Three lenses (Adversarial, Edge-Case Hunter, Verification Gap) ran against the diff, explicitly weighting the seams between the four stories and told to focus on cross-story interactions rather than re-finding what each story's own thorough review already caught and fixed. I additionally checked directly whether Story 1.4's own rule ("no icon-only control ships without an accessible name") held across every later epic.

### Real, verified — new findings this retrospective surfaced

- **Registration's rollback path leaves a dangling session cookie.** `app/api/auth/register/route.ts`: when `createProfile()` throws after `supabase.auth.signUp()` already succeeded, the handler deletes the orphaned Auth user via the admin client (the exact fix Story 1.1's own review applied) but never clears the session cookies `signUp()` already staged on the response. Verified by reading the route's rollback branch — no `supabase.auth.signOut()` or cookie-clearing call exists there. The browser is left holding a session cookie for a user id that request just told the admin API to delete, until the next revalidation catches it. (Adversarial and Edge-Case Hunter, independently converged.)
- **Register's client-side form never enforces `MAX_DAILY_CALORIE_TARGET`.** `lib/constants.ts` documents itself as "the single source of truth for register, preferences (client + server), and any future caller," and `preferences-form.tsx` does check it client-side — but `app/(routes)/register/page.tsx`'s own validation (line 40) only checks `!Number.isInteger(target) || target <= 0`, never importing the constant. Verified directly: grepping `MAX_DAILY_CALORIE_TARGET` across `app/`/`lib/` shows it used in the preferences form, the register *route*, and the preferences *route* — never the register *page*. An over-limit signup value is silently accepted client-side and only rejected after a full round trip to the server, contradicting the constant's own documented contract. (Verification Gap and Edge-Case Hunter, independently converged.)
- **No deep-link preservation across the login redirect — and the condition that was supposed to trigger revisiting this has now happened.** Story 1.2's own review deferred this exact gap with an explicit revisit condition: "zero user-visible impact today since `/` is the only protected route that exists; revisit once Epic 2+ adds real protected routes." Verified directly: `proxy.ts` still redirects to a bare `/login` with no `?next=` param, and `login/page.tsx` still hard-navigates to `/` unconditionally on success — unchanged since Story 1.2. Since then, Epic 5 added `/trends` and this same epic added `/preferences`, both real, deep-linkable, protected routes. A user whose session expires while on `/preferences` (or who follows a shared/bookmarked link there while logged out) is now silently dropped at the Daily view instead of their destination — the deferred item's own stated trigger condition is now true, but nobody revisited it, because no single subsequent story's own review would think to check a different story's already-closed deferral. (My own finding, independently converged with Adversarial and Edge-Case Hunter.)
- **No logout affordance exists anywhere in the app — and it was never once specified.** Grepped the entire codebase (`app/`, `components/`, `lib/`) for `signOut`/`logout`/`sign out`: zero matches. Also grepped every planning artifact (PRD, epics, UX designs): zero mentions of logout anywhere. This is not a story implementation failure — no AC in Epic 1 or anywhere else ever asked for it — it's a gap in the product's own planning that only becomes visible once the whole auth lifecycle (register → login → gated routes) is considered as a complete unit, which is exactly what individual story reviews don't do. (Adversarial.)
- **The Preferences page has no way back to the Daily view.** Verified: no `href="/"` or any "Back"/"Home" text anywhere in `app/(routes)/preferences/page.tsx`. Converges with Epic 0's own retrospective finding about `/trends` having the identical gap — `/preferences` is where this pattern actually originated (Story 1.3, this epic), predating Trends by four epics. (Adversarial, and cross-referenced with the Epic 0 retro.)
- **A stale "temporary" comment sits atop the real, permanent, production Daily view.** `app/page.tsx:14`: "Temporary foundation showcase for Epic 0 (UX Foundation)... Replaced by the actual Daily view in Epic 3." Epic 3 shipped years — epics — ago; this is now the real, permanent Daily view, not a showcase awaiting replacement. Every epic since (3, 4, 5) added its own new comments around this one without anyone revisiting or removing the now-false header, because it was never part of any of their own diffs. (My own finding, verified directly.)

### Verified false or already-addressed — reported but not carried forward

- **Register's `router.push("/")` vs. Login's `window.location.href = "/"`** was raised independently by all three lenses as a suspicious asymmetry, since Login's own review found and fixed a real cookie-race bug with this exact shape. Verified directly (read the actual code path): Register's session cookie is set via the *server's* `Set-Cookie` header on the completed `/api/auth/register` HTTP response — guaranteed synced to the browser's cookie jar before the `fetch()` promise even resolves, let alone before `router.push()` runs. Login's original bug was the browser client's own in-page `document.cookie` write racing a soft navigation — a structurally different, riskier pattern Register never uses. This exact comparison was already investigated by Story 1.2's own review, with the same conclusion recorded in its Review Triage Log; I independently re-confirmed the reasoning still holds against the current code. Not a live bug.
- **`app/(routes)/preferences/page.tsx`'s unguarded `getProfile()` call** (a thrown error crashes the page render if a profile row is missing) was raised by Edge-Case Hunter. Already found and explicitly deferred in Story 1.3's own review: defensive-only (the row is guaranteed at registration, never deleted independently), and no route in this codebase has an `error.tsx` boundary yet, so a one-off fix here would be inconsistent rather than corrective. No new action.
- **Plain `<a>` tags instead of `next/link`** for internal navigation was raised by Adversarial. Already investigated and explicitly accepted in Story 1.4's own review: consistent with the rest of the codebase, which uses plain `<a>` everywhere, not a Story-1.4-specific shortcut.

### Real but low-impact — logged, not actioned this round

- Duplicate-email detection's `data.user.identities?.length === 0` check wouldn't catch a hypothetical Supabase response shape where `identities` is `undefined` rather than an empty array. Converges with Story 1.1's own already-deferred "exact-match/behavior-assumption against live Supabase, no test" gap — a refinement of that same root cause, not a new one.
- `proxy.ts`'s matcher excludes only 4 named public files, not `/public` assets generally — currently dormant: `public/` is empty and neither auth page references any asset there. Revisit only if a real static asset is ever added.
- `dietary_preference`'s silent-coerce-to-default vs. the sibling missing-profile-row's thrown error are inconsistent trust boundaries for the same class of "should never happen" state — both sides are individually-accepted, already-deferred patterns from Story 1.3's own review; not worth reconciling on its own.
- `MIN_PASSWORD_LENGTH`/`DEFAULT_DAILY_CALORIE_TARGET` remain local to `register/page.tsx` rather than joining `MAX_DAILY_CALORIE_TARGET` in `lib/constants.ts` — minor consistency nit, no current drift.
- Hardcoded Supabase/GoTrue error-message literals (`"User already registered"`, `"Invalid login credentials"`) are duplicated across Register and Login with no shared constant or regression test — matches this codebase's already-accepted, hand-rolled-validation convention elsewhere (no shared schema library anywhere yet, per Story 1.3's own review).
- `/api/preferences`'s own defense-in-depth `401 unauthenticated` branch is surfaced as a generic inline error by the client rather than a redirect to `/login` — only the proxy-triggered `response.redirected` path gets the redirect treatment. Narrow: only matters if proxy's route coverage is ever changed.
- Register's single `catch` block can't distinguish "network failure before signup" from "signup succeeded but the client's own post-success bookkeeping (`getSession()`/`router.push()`) threw" — a rare failure mode that would show a misleading "couldn't reach the server" message for an account that was, in fact, created.

## Acceptance verdict

**Accepted-with-open-items.** Criteria profiled from the four stories' own ACs (epics.md has no separate Epic-1-level AC). All four stories are `done`, `pending_stories` empty. The epic's core promise — accounts can be created, sessions gate every non-public route by default, and Preferences reads/writes the right data — holds correctly and was already exercised hard by each story's own review (which caught and fixed several genuinely serious bugs, e.g. the orphaned-Auth-user rollback and the proxy cookie-forwarding footgun, before this retrospective ever ran). Set against that: six real, verified gaps surfaced only by looking across all four stories together, including one deferred item whose own stated revisit trigger has now fired and gone unnoticed for multiple epics, and a product-level gap (no logout) that was never even specified. None of these make the epic's foundation unusable — every later epic successfully built directly on top of it — but they're real and open, not silently accepted.

- Should the shared "back to Daily view" nav affordance (action item 5) also become the natural home for a logout action (item 4), if the human decides logout is wanted? Bundling the two would avoid a second round of nav-surface changes.
