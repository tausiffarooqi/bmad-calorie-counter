## Intent

**Problem:** The Daily view shows a single hardcoded placeholder Recommendation card; nothing computes real recommendations from time-of-day, remaining Meal Slots, or Dietary Preference, and neither API response actually returns them yet (FR-9's response contract is unfinished).

**Approach:** Add a `recommendation-engine` service: a static, versioned lookup table keyed by (Meal Slot, Dietary Preference), and a pure function computing which slots (lunch/dinner) are still open for the current local hour minus already-logged Meal-classified Entries today (AD-7, compute-don't-store). Wire it into both `GET /api/entries` (Daily view load) and `POST /api/entries` (per-submission response, completing FR-9's contract). Replace the Daily view's hardcoded card with 0–2 real, data-driven cards.

## Boundaries & Constraints

**Always:** Expected Meal Slots for the current local hour: `["lunch","dinner"]` for 5am–12pm, `["dinner"]` for 12pm–10pm. Filled-slot count = count of `classification: "meal"` Entries logged today (compute-don't-store, AD-7) — snack/beverage Entries never reduce it. Remaining slots = expected slots minus filled count, earliest slot first (lunch fills before dinner) — matches EXPERIENCE.md's own ordering ("Two Recommendation cards stack, lunch then dinner"). Same (slot, Dietary Preference) key always returns identical text (AD-8) — this is expected, not a staleness bug. `profiles.dietary_preference` always resolves (defaults to `non_vegetarian`, Story 1.1) — the lookup never hits an undefined case. `POST /api/entries` now requires a `tz` field in its request body (mirroring `GET`'s query param) to compute the response's `remainingBudget`/`recommendations` against the correct local day/hour.

**Never:** Do not implement the 10pm–5am window (Story 3.4's "After-10pm Conditional Recommendation") — for now, local hours outside 5am–10pm resolve to zero expected slots. Do not implement Over-Target suppression or an Over-Target-flavored recommendation variant (Story 3.5) — per EXPERIENCE.md's own State Patterns, the Over-Target banner always *replaces* the Recommendation card entirely, so no over-target-specific lookup entry is ever needed; the lookup table stays two-dimensional (slot × Dietary Preference) only. Do not add a breakfast slot (Epic 4). Do not persist a slot-fill counter anywhere — it's always derived. Do not add per-Entry Meal-Slot labeling to the Entries list (out of scope, no data model support, not in any current story's AC).

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| 5am–12pm, zero Meals logged | Local hour 8am, 0 `meal`-classified Entries today | 2 recommendations: `[{slot:"lunch",...}, {slot:"dinner",...}]` | N/A |
| 5am–12pm, one Meal logged | Local hour 10am, 1 `meal`-classified Entry today | 1 recommendation: `[{slot:"dinner",...}]` | N/A |
| 12pm–10pm | Local hour 3pm, 0 Meals logged | 1 recommendation: `[{slot:"dinner",...}]` | N/A |
| All expected slots filled | Local hour 3pm, 1+ Meals logged | `[]` — no cards | N/A |
| Snack/Beverage logged, slots unaffected | Any time, 1 `snack_beverage` Entry, 0 `meal` Entries | Slot count unchanged from the zero-Entries case | N/A |
| `POST` submitted with a missing/invalid `tz` | Request body has no valid `tz` string | 400, same `{ error: { code: "invalid_input", ... } }` shape as other `POST` validation failures | Existing pattern, new field |
| Outside 5am–10pm (e.g. 2am) | Local hour 2 | `[]` — zero expected slots (Story 3.4 defines this window later) | N/A |

## Implementation Notes

- `lib/services/recommendation-engine.ts` (new): `MEAL_SLOTS = ["lunch", "dinner"]`/`MealSlot`; static `RECOMMENDATION_COPY: Record<MealSlot, Record<DietaryPreference, string>>` with exactly 4 entries (dinner/vegetarian reuses the previously-hardcoded approved copy verbatim); `getRecommendations(now, tz, entries, dietaryPreference)` reads the local hour via a standalone `Intl.DateTimeFormat` read (same `hourCycle:"h23"`/midnight-as-"24" technique as `day-boundary.ts`'s `getLocalParts()`, not an import of its unexported helper), maps the hour to expected slots (5am-12pm -> both, 12pm-10pm -> dinner only, else -> none), counts `classification === "meal"` Entries, and slices the expected-slots array by that count (earliest slot first) to get the remaining slots. Pure/sync, no DB access. Imports `Classification`/`DietaryPreference` via a relative `"../constants.ts"` import (not the `@/*` alias), matching `entry-classifier.ts`'s convention, since this file is also exercised directly by `node --test`.
- `lib/services/recommendation-engine.test.ts` (new): 15 tests covering every I/O & Edge-Case Matrix row (zero-Meals/one-Meal in the morning window, midday window, all-slots-filled, Snack/Beverage-doesn't-fill-a-slot, outside-5am-10pm) plus window-boundary tests (04:59/05:00, 11:59/12:00, 21:59/22:00), the AD-8 same-key-same-text-across-days invariant, the non_vegetarian-default-resolves guarantee, the verbatim dinner/vegetarian copy reuse, and a table-shape check (4 populated entries).
- `lib/get-client-timezone.ts` (new): `getClientTimeZone()` wraps `Intl.DateTimeFormat().resolvedOptions().timeZone`. Adopted by `hooks/use-daily-view.ts` (replacing its inline duplicate) and newly by `app/log-entry-dialog.tsx`/`app/log-photo-dialog.tsx`.
- `app/api/entries/route.ts`: `POST` now parses/validates a `tz` body field (`typeof tz === "string" && isValidTimeZone(tz)`) right after the auth check, before the existing text/photo XOR validation and before the Gemini call — same `{ error: { code: "invalid_input", ... } }` 400 shape as the existing validation failures. After `createEntry()` succeeds, the handler re-fetches today's Entries + profile fresh (`dayBoundary(new Date(), tz)` + `getEntriesForDay`/`getProfile`, run concurrently) so the just-created Entry is itself included in both the budget subtraction and the filled-slot count, computes `remainingBudget`/`recommendations`, and returns them alongside `calories` in the `{ ok: true, ... }` response (FR-9). A missing profile or any failure in this follow-up step returns the existing `entry_creation_failed` 500 shape (the Entry itself is already durably persisted at that point; only the response-enrichment step failed, logged with its own distinct message). `GET` calls `getRecommendations()` using the already-fetched `rows`/`profile` (no second `entries` query) and adds `recommendations` to its response alongside the existing `entries`/`remainingBudget`. Two small local helpers narrow the DB's plain-`text` columns to their app-level union types for `getRecommendations()`'s signature: `toDietaryPreference()` (mirrors `preferences/page.tsx`'s existing `=== "vegetarian" ? ... : "non_vegetarian"` pattern for the same column) and `toRecommendationEntries()` (equivalent narrowing for `classification`, guaranteed correct by `createEntry()`'s own required, `Classification`-typed parameter — AD-1).
- `hooks/use-daily-view.ts`: `EntriesApiResponse` gains an optional `recommendations?: Recommendation[]` field; the hook now also `setRecommendations(result.recommendations ?? [])` and returns `recommendations` alongside `entries`/`remainingBudget`/`loadError`.
- `app/log-entry-dialog.tsx` / `app/log-photo-dialog.tsx`: both now send `tz: getClientTimeZone()` in their POST bodies alongside the existing `descriptionText` / `photoBase64`+`photoMimeType` fields.

## Design Notes

- **No Over-Target axis in the lookup table.** EXPERIENCE.md's State Patterns are explicit: "Over-Target banner replaces every Recommendation card at once" — there is no "over-target-flavored card" state in the design at all, only present-card vs. absent-card-plus-banner. Building an unused axis now would be dead code until (and possibly even after) Story 3.5 exists.
- **Slot-fill ordering is positional, not identity-tracked.** Entries carry no per-Entry slot tag (only `classification: meal | snack_beverage`), so "which slot got filled" is inferred purely from count, earliest-expected-slot-first — matching EXPERIENCE.md's own worked example (lunch fills before dinner). This is a deliberate simplification, not an oversight: the alternative (tagging each Entry with an explicit slot) isn't supported by the data model and isn't required by any AC.
- **Recommendation copy** (4 entries, 2 slots × 2 Dietary Preferences) reuses the one existing approved example verbatim (dinner/vegetarian: "Try a grilled paneer wrap with sautéed greens.") and adds three more in the same plain, non-scored, supportive tone (no confidence/match language, per EXPERIENCE.md's explicit rejection of that pattern).
