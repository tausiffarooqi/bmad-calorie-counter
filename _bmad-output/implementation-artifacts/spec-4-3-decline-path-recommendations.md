## Intent

**Problem:** Story 4.3's AC requires that declining the First-Login prompt's log-a-meal ask ("Not now") never leaves the user at a dead end — they must land on the Daily view with its normal Recommendation card(s) (or the Over-Target banner, if applicable) for the remaining Meal Slots.

**Approach:** No new code. Investigation confirms this is already fully satisfied as a side effect of Story 4.1 + Epic 3's existing, frozen implementation — see Implementation Notes for the exact mechanism traced. This story exists to record that verification, not to add a feature.

## Implementation Notes

- Traced the exact decline mechanism in `app/page.tsx`: both `FirstLoginPrompt` buttons ("Log a meal" and "Not now") call the same `onResolve = () => setPromptDismissed(true)` (Story 4.1, frozen — both buttons resolve to the same next state, no dialog auto-opens). Setting `promptDismissed` flips `showPrompt` (`budgetReady && showFirstLoginPrompt && entries.length===0 && !promptDismissed`) to `false` synchronously, client-side only — no second network round-trip, since the server already marked the prompt shown at the original `GET` that produced `showFirstLoginPrompt: true`.
- Once `showPrompt` is `false`, `app/page.tsx`'s existing ternary (`showPrompt ? <prompt branch> : <normal Daily view branch>`, lines 104-202 in the current file) renders immediately: the budget header (now unhidden since `!showPrompt`), `EntriesList`, and — critically — the same `!loadError && isOverTarget` Over-Target banner / `!loadError && !isOverTarget && recommendations.map(...)` Recommendation-card rendering (lines 160-186) used on every other visit to the Daily view. The ternary itself was introduced in Story 4.1 (its own comment at line 104 attributes it: "Story 4.1: replaces the entries list, Recommendation cards/Over-Target banner ... at once"), with Story 4.2 later nesting a `toneMessage` block inside the prompt branch (lines ~118-122) — only the Recommendation-card/Over-Target-banner rendering logic itself (lines 160-186) is unchanged since Story 3.5, not the surrounding ternary. `recommendations` and `remainingBudget` are already present in the `useDailyView()` result from the very same fetch that produced `showFirstLoginPrompt: true` — `GET /api/entries` computes `recommendations` via `getRecommendations()` unconditionally, never gated on `showFirstLoginPrompt` (confirmed in `app/api/entries/route.ts`). No stale/loading flash: `firstLoadPending`/`budgetReady` only track the *first* fetch's resolution, which by construction has already completed by the time either button is tappable.
- `toneMessage` (Story 4.2) is scoped entirely to the `showPrompt` branch — rendered only alongside `FirstLoginPrompt` — and simply stops rendering once `promptDismissed` flips `showPrompt` false. This is intentional per Story 4.2's own frozen Boundaries & Constraints ("Do not compute or return this message when the First-Login prompt isn't showing"), not a separate concern this story needs to handle.
- **AC 1 (normal Recommendation cards render on decline)**: satisfied with zero code changes — confirmed by the trace above, consistent with the epic context's own Cross-Story Dependencies note ("Story 4.3 ... directly reuses whatever the Daily view already renders").
- **AC 2 (Over-Target banner renders on decline, when applicable)**: also goes through the identical, already-shared rendering path — no separate implementation exists or is needed. One structural note worth recording: the First-Login prompt (and therefore the decline path) only ever shows when `entries.length === 0` for the Day (Story 4.1's own frozen guard, added to prevent hiding already-logged Entries behind the prompt). Over-Target (`remainingBudget < 0`) requires Entries summing past `dailyCalorieTarget`, which cannot be true while `entries.length === 0` *and* `dailyCalorieTarget` stays positive. That positivity is enforced outside this story's own four files, at both write paths that can set it — `app/api/auth/register/route.ts` and `app/api/preferences/route.ts` both reject `dailyCalorieTarget <= 0` (verified directly, not assumed). So the exact "decline while already Over-Target" combination is currently structurally unreachable through this specific entry point — not a gap, a direct, correct consequence of Story 4.1's frozen Boundaries & Constraints plus that external validation, and not something this story's scope (reusing existing rendering) is positioned to change. If a future story ever loosens that validation or changes the prompt's visibility conditions, the shared rendering path already handles Over-Target correctly regardless, so no follow-up implementation would be needed then either.
- **Scope note**: this trace equally covers the "Log a meal" (accept) tap, since `first-login-prompt.tsx`'s own comment confirms both buttons call the identical `onResolve` — neither opens a logging dialog directly (Story 4.1's own resolved Open Question: "Just reveal the buttons"). Story 4.3's AC is written against the decline path specifically, but the underlying mechanism verified here is shared and applies identically regardless of which button was tapped.

That code-level guarantee holds regardless of this session's live-verification status. A live click-through would only catch an environment-specific integration issue (e.g., a runtime error the static trace can't see), not a logic gap the trace has already ruled out — it's a residual-risk check, not a precondition for the AC being satisfied.
