## Findings

Three lenses ran against the diff, explicitly told what Story 4.4's own loopback already fixed so they wouldn't re-report it. All three independently converged on the same two findings from different angles — the strongest cross-lens agreement of this retrospective series.

### Real, verified — the headline finding (triple-converged)

- **Accepting the breakfast offer silently dismisses the unrelated, still-open First-Login prompt and its tone message.** `useDailyView`'s `showFirstLoginPrompt` state (`hooks/use-daily-view.ts`) is unconditionally overwritten on every fetch: `setShowFirstLoginPrompt(result.showFirstLoginPrompt ?? false)`. `checkAndMarkFirstLoginPrompt()` is one-shot-per-Day — it already marked `lastFirstLoginPromptAt` on the very first `GET` of the load. `handleAcceptBreakfastOffer()` calls `bumpRefreshKey()` unconditionally after its `POST` (success or failure), forcing a second `GET`, which legitimately returns `showFirstLoginPrompt: false` this time. `app/page.tsx`'s `showPrompt = budgetReady && showFirstLoginPrompt && entries.length===0 && !promptDismissed` re-evaluates to `false` purely because of this side-effect refetch — `promptDismissed` (set only by card 1's own two buttons) never became `true`. The user resolves card 2 (breakfast); card 1 (the log-a-meal prompt) and Story 4.2's tone message vanish along with it, with no action taken on either. This directly contradicts the explicit, repeatedly-quoted invariant both stories' own frozen specs establish: "the two cards ... resolve independently." Verified directly by reading `use-daily-view.ts`'s unconditional state overwrite, `profiles.ts`'s one-shot check, and `page.tsx`'s `showPrompt` derivation. Neither story's own isolated review could have caught this — Story 4.1's review predates the breakfast card entirely, and Story 4.4's review only verified the offer card's own reappearance-on-reload, never its side effect on card 1 via the shared `refreshKey`/`useDailyView` mechanism. (Verification Gap, Edge-Case Hunter, and Adversarial — all three, independently.)
- **The breakfast-offer accept endpoint's server-side eligibility check doesn't verify entries the way the display logic does.** `app/api/breakfast-offer/route.ts`'s `POST` handler fetches `rows` (today's entries) solely to compute `remainingBudget` — it never checks `rows.length` or classification, only `isBreakfastOfferWindow(now, tz)` and `remainingBudget < 0`. `GET /api/entries`'s own `showBreakfastOffer` requires `rows.length === 0` ("never shown once a Meal/Snack is logged," per that route's own comment). A stale client (a backgrounded tab, a second device, or a direct API call) can still successfully persist `breakfastOfferAcceptedAt` after an Entry already exists for the Day — a state the card's own visibility rule was specifically designed to prevent from ever being reachable, contradicting the route's own comment claiming this exact block ensures a stale/replayed accept "must not silently persist." Verified directly: read the full eligibility block, confirmed no `rows.length`/classification check exists anywhere in it. (Verification Gap, Edge-Case Hunter, and Adversarial — all three, independently.)

### Real, verified — additional findings (single-lens, independently confirmed by me)

- **`showBreakfastOffer`'s own gate is classification-blind, inconsistent with the slot-fill logic it feeds.** It requires `rows.length === 0` (any Entry at all), copied from Story 4.1's log-a-meal-prompt gate — but `getRecommendations()`'s own `filledCount` explicitly only counts `classification === "meal"` Entries, ignoring Snack/Beverage ones (Story 3.3's established rule). Logging a single snack (e.g. a morning coffee) before 10am permanently hides the breakfast-offer card for the rest of the day, even though the breakfast Meal Slot is still completely open. The inconsistency is baked into Story 4.4's own frozen Code Map, which copied 4.1's criterion without reconsidering whether it fits a card whose entire job is tracking a specifically-typed Meal Slot. (Adversarial.)
- **`isBreakfastOfferWindow`'s `hour < 10` check doesn't exclude the midnight-5am hours, creating a permanent dead end for early-morning logins.** Those hours belong to the *same* Day (AD-5's 5am boundary — anything before 5am is still "yesterday's" still-open Day), but `expectedSlotsForHour`'s own after-10pm/before-5am branch never reads `breakfastOffered` at all — it only ever returns `["dinner"]` or `[]`. A night-shift worker or insomniac who first opens the app at, say, 3am sees and can accept the breakfast offer, and the acceptance durably persists — but no breakfast recommendation can ever result: not in the current window (which ignores the flag), and not on the *next* Day either (the accepted timestamp falls before that Day's own `dayBoundary` start). The offer becomes a silent, permanent no-op. `recommendation-engine.test.ts`'s four `isBreakfastOfferWindow` tests only exercise 08:00/09:59/10:00/15:00 — none exercise the 0-5 dead zone. (Adversarial, logic independently re-verified.)
- **`acceptBreakfastOffer()`'s internal `getProfile()` call is now a genuinely avoidable, redundant DB round-trip.** Its own comment claims "its only caller ... never fetches a profile of its own beforehand, so there's nothing to reuse" — but that comment predates the server-side eligibility-check fix, which now *does* fetch `profile` via `Promise.all` before ever calling this function. The comment is stale, and the extra fetch is now pure waste, introduced because two separately-motivated fixes from the same review-loopback pass (adding the eligibility block; writing that exact comment) were never cross-checked against each other. (Adversarial, verified directly.)

### Real but low-impact — logged, not actioned this round

- `checkAndMarkFirstLoginPrompt()`'s write can still be "wasted" if a *later* step in the same request (`getRecommendations()`) throws afterward — the fix that sequenced the mark-write after the primary reads succeed didn't account for this later failure point. Narrow: `getRecommendations()` is a pure function not expected to throw in practice, matching the same "defensive-only, unreachable in practice" precedent already established for similar findings in Epic 3's retro.
- `checkAndMarkFirstLoginPrompt()` itself never checks entries — only the client's `entries.length === 0` guard prevents the prompt from rendering when another device already logged something. The server still burns the one-shot flag and still computes Story 4.2's tone message on that Day, wastefully but harmlessly (nothing is shown, nothing is lost beyond one unread computation).
- `breakfastOfferAccepted` is computed, returned by the API, and given a detailed justifying comment in `hooks/use-daily-view.ts` — but no component anywhere actually reads it. Dead API surface, harmless.
- A transient refetch failure immediately after a successfully-persisted breakfast-offer acceptance can transiently re-show the offer card (since `loadError` doesn't reset other stale fields) — confusing but harmless, since re-accepting is idempotent.
- `previousDayBoundary` (Story 4.2) inherits the already-documented DST fall-back ambiguity at a new call site without updating the limitation note to mention it. Documentation completeness only; the underlying ambiguity was already known and accepted.

## Action items

1. **Stop an unrelated refetch from silently collapsing the still-open First-Login prompt.** Latch "the prompt was shown this session" (e.g. a ref set once `showFirstLoginPrompt` is first observed true) so only the user's own `promptDismissed` action can hide card 1 — not a later refetch's fresh (and correctly one-shot-false) server value. Owner: next dev session.
2. **Make the breakfast-offer accept endpoint's eligibility check match the display logic's entries/classification gate**, mirroring `GET /api/entries`'s own `rows.length === 0` (or better, the classification-aware version from item 3) rejection. Owner: next dev session.
3. **Make `showBreakfastOffer`'s gate classification-aware**, matching `getRecommendations()`'s own "only Meal-classified Entries count" rule, instead of the coarser `rows.length === 0` copied from Story 4.1's unrelated card. Owner: next dev session.
4. **Exclude midnight-5am from `isBreakfastOfferWindow`** so the offer is never shown/acceptable during the hours where accepting it can never produce a recommendation. Owner: next dev session.
5. **Thread the already-fetched `profile` into `acceptBreakfastOffer()`** instead of re-fetching internally, and correct its now-stale comment. Owner: next dev session (small, mechanical).
