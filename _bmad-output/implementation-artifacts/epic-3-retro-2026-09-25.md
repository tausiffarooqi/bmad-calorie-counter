## Findings

Three lenses ran against the diff, told to focus on cross-story seams. I additionally re-verified that `computeRemainingBudget`/`getRecommendations` remain centralized to their two expected call sites (no duplication drift since).

### Real, verified — the headline finding

- **A real breakfast, logged in normal usage, silently consumes the "lunch" recommendation slot.** All three lenses converged on variations of this, with Verification Gap pinpointing the exact trigger: `lib/services/entry-classifier.ts`'s `MEAL_KEYWORDS` literally includes the word `"breakfast"` — so a description like "scrambled eggs and toast for breakfast" classifies as `"meal"`, exactly as Story 3.1 intended (a binary meal-vs-snack decision, which is all that story's own scope covers). But `recommendation-engine.ts`'s slot-fill logic (`filledCount = entries.filter(e => e.classification === "meal").length`, then `expectedSlots.slice(filledCount)`) is purely positional and count-based — it has no concept of *which* meal was eaten, only *how many*. In the 5am-12pm window, `expectedSlots` is `["lunch", "dinner"]`; a single breakfast-classified Entry sets `filledCount = 1`, and `slice(1)` silently drops "lunch" — the user sees only a Dinner Recommendation, as if they'd already eaten lunch, when they haven't. Verified directly: read `MEAL_KEYWORDS` (confirms "breakfast" is present), read the slice logic (confirms it's purely positional), read both stories' frozen specs and Design Notes (confirms "breakfast" is never mentioned in either — this exact interaction was never discussed when either story was written), and confirmed Story 4.4's later `breakfastOffered` mechanism is a separate, UI-opt-in flag that doesn't touch or fix this — `filledCount` still counts every `"meal"`-classified Entry identically regardless of what it actually was. This is a different, narrower problem than the already-accepted "slot-fill is positional, not identity-tracked" design note (which was scoped to lunch/dinner ambiguity between themselves) — here, an entirely unmodeled meal type (breakfast) is silently absorbed into the tracked lunch/dinner pool. Not a rare edge case: any user who types the ordinary word "breakfast" hits this on the very first try. (Adversarial, Edge-Case Hunter implicitly via the positional-slicing observation, and Verification Gap — all three independently, the strongest convergence of this retrospective series so far.)
- **`GET` and `POST` handle an identical failure (missing `profiles` row) with different severities in the same file.** `GET`'s `if (!profile)` branch fails the *entire* request (the user can't even see today's already-logged Entries) — verified directly in the current code. `POST`'s equivalent branch (`if (!freshProfile)`) gracefully degrades, falling back to `{ ok: true, calories }` without the enrichment. Both conditions represent the exact same underlying state; only `GET` treats it as fatal. Verified by reading both branches side by side. (Adversarial, and independently noted by Edge-Case Hunter as one of its findings.)
- **The Remaining Calorie Budget number falls back to a perpetual, ambiguous loading skeleton on a genuine fetch failure, while the Entries list — fed by the exact same fetch — shows an explicit, distinct alert.** `app/page.tsx`'s `budgetReady` gate (`remainingBudget !== undefined && !loadError`) intentionally avoids showing a *stale* number on failure (a deliberate, documented Story 3.2 decision) — but the fallback it reuses (the cold-load `animate-pulse` skeleton) implies "still loading," not "failed," giving the same `loadError` state two different user-facing meanings depending on which piece of UI you're looking at. Verified directly by reading both render branches. (Edge-Case Hunter.)
- **`recommendation-engine.ts`'s `getLocalHour()` duplicates `day-boundary.ts`'s hour-extraction logic** (`Intl.DateTimeFormat` with `hourCycle:"h23"`, normalizing midnight's `"24"` to `0`) instead of importing a shared helper — the file's own comment acknowledges this was a deliberate choice at the time ("a narrower, standalone read... rather than an import of that file's unexported helper"), but it means a future timezone/DST fix discovered in one copy has no structural reason to also land in the other. (Adversarial.)
- **`POST`'s enrichment `now` is captured after `classify()`/`createEntry()` already ran**, not before — for a slow photo-mode Gemini call straddling a Day-boundary instant, the response's `remainingBudget`/`recommendations` could in principle reflect a slightly different moment than the entry's own DB-recorded `created_at`. Converges thematically with Epic 2's retro finding about a similar 5am-boundary race in `entries-list.tsx` — both are "an async delay lets the Day boundary roll over between capturing `now` and using it" in different parts of the same feature area. Extremely narrow window in practice. (Adversarial.)

### Verified false or already-addressed

- Two of Edge-Case Hunter's claims were checked directly and found false: `getEntriesForDay()`'s plain `.select()` already selects every column including `classification` (no projection gap), and the `classification` migration (`drizzle/0003_same_ikaris.sql`) already correctly backfills existing rows with a temporary default before dropping it — both already handled exactly as claimed to be missing.
- POST's `remainingBudget`/`recommendations` enrichment fields being unconsumed by the dialogs (Adversarial, Edge-Case Hunter) — already found and explicitly accepted in Story 3.3's own review as a deliberate FR-9-contract-fulfillment decision, logged in `deferred-work.md`. Not new.
- No cheap retry path after a photo-mode classification failure forcing a full resubmission (Adversarial) — already found and deferred in Story 3.1's own review, logged in `deferred-work.md`. Not new.
- No route-level test coverage for `route.ts`'s wiring (Adversarial) — the same project-wide, repeatedly-confirmed gap logged many times over.

### Real but low-impact — logged, not actioned this round

- Client re-derives `isOverTarget` (`remainingBudget < 0`) independently in `app/page.tsx` rather than the API returning an explicit flag — currently harmless (mathematically identical to the server's own check) but a duplicated source of truth that could silently desync if the threshold or precedence ever changes.
- `POST`'s `tz` field became required (400 if missing) in the same commit that shipped the paired frontend change sending it — a theoretical rolling-deploy/stale-client-bundle risk, but disproportionate for this project's actual single-developer, atomic-deploy hobby scale.
- `hooks/use-daily-view.ts`'s tz is captured once per fetch, not re-derived on window focus/visibility change, even though its output now feeds time-sensitive guidance (budget, recommendations, Over-Target banner) rather than just a passive list. Narrow: only matters if a user changes timezones without logging anything new.

## Action items

1. **Decide how to handle meal types the classifier can identify by keyword but the recommendation engine doesn't model as slots (starting with "breakfast").** This is the epic's headline finding — a real, easily-reproduced gap where an ordinary breakfast entry silently consumes the "lunch" position. Needs a product/design decision, not a unilateral code fix: options include giving Meal Slots real time-of-day identity (compute which slot an Entry's own `createdAt` hour actually falls into, rather than positional depletion), or relabeling the "lunch"/"dinner" cards to not imply a specific meal has or hasn't happened yet. Owner: human decision needed first.
2. **Make `GET`'s missing-profile handling degrade gracefully, matching `POST`'s own precedent in the same file.** `app/api/entries/route.ts`'s `GET` handler — on a missing/failed profile, still return the entries list with budget/recommendations simply omitted, instead of failing the whole response. Owner: next dev session.
3. **Give the Remaining Calorie Budget number its own explicit failure state**, distinct from the cold-load skeleton, matching `EntriesList`'s existing `role="alert"` treatment for the identical `loadError` condition. Owner: next dev session.
4. **Export a shared local-hour helper from `day-boundary.ts`** and have `recommendation-engine.ts` import it instead of maintaining its own independent copy of the same `Intl.DateTimeFormat`/midnight-normalization logic. Owner: next dev session (small, mechanical).
