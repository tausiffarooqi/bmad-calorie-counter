## Intent

**Problem:** Breakfast never gets its own Recommendation today — `getRecommendations()` only knows `lunch`/`dinner`. A user who checks in before 10am has no guidance for that meal slot at all.

**Approach:** When first login occurs before 10am, show a second card ("Want a breakfast recommendation too?") alongside the existing log-a-meal prompt. Accepting adds `breakfast` as a genuinely additive third Meal Slot in `getRecommendations()`'s 5am-12pm window — lunch/dinner unaffected — persisted per-Day (new `profiles.breakfast_offer_accepted_at` column, mirroring Story 4.1's `last_first_login_prompt_at` pattern) so the extra slot survives a reload after the offer is accepted but before breakfast is logged. Declining is not persisted (client-only for that page session, may reappear on a same-day reload before 10am — an accepted, documented tradeoff, consistent with Story 4.1's already-accepted multi-device/reload redundancy gap). Over-Target State suppresses the offer exactly like every other recommendation path (Story 3.5, no separate implementation). **Decision:** acceptance tracking is persisted (new DB column), not ephemeral/client-only — confirmed explicitly, since the ephemeral option would silently miscount lunch/dinner after a reload following "accept breakfast, log it, reload before lunch."

## Boundaries & Constraints

**Always:** The breakfast-offer card and the existing log-a-meal card (Story 4.1) resolve independently — accepting/declining one never depends on or blocks the other. This is required, not a style choice: Story 4.3's already-shipped, already-verified spec traced that declining the log-a-meal card immediately reveals the full Daily view via `promptDismissed` alone; coupling the two cards into one combined dismissal would silently invalidate that already-committed contract. The breakfast Recommendation card (once accepted) renders through the exact same `recommendations.map(...)` block every other Recommendation card uses — no distinct visual treatment, no new component for the recommendation card itself, only for the offer card. `getRecommendations()`'s existing 5-argument call sites (POST's post-submission recompute, GET) both gain the same new optional 6th argument — never a breaking signature change to any of the ~25 existing test call sites, which must keep passing unmodified.

**Never:** Do not gate the breakfast slot's persistence on anything but a per-Day comparison against `breakfast_offer_accepted_at`, the same `dayBoundary()`-based pattern `checkAndMarkFirstLoginPrompt` already uses — no separate/inline date math (AD-5). Do not extend the offer's effect past the 5am-12pm window once the window itself has moved on (mirrors how an unlogged lunch Recommendation already disappears once the midday window passes — breakfast gets no special exemption). Do not touch `FirstLoginPrompt` (Story 4.1, frozen) or the tone-message rendering (Story 4.2, frozen). Do not persist a decline — only acceptance is written.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| First login before 10am, not yet resolved today | `showFirstLoginPrompt`, `entries.length===0`, local hour < 10, `breakfast_offer_accepted_at` not today | Breakfast-offer card renders (independent of the log-a-meal card's own state) | N/A |
| First login at/after 10am | Same as above but local hour >= 10 | No breakfast-offer card at all | N/A |
| Already accepted today, reloaded before logging breakfast | `breakfast_offer_accepted_at` within today's Day window | No offer card (already resolved); `getRecommendations()` includes `breakfast` as an open slot alongside lunch/dinner | N/A |
| Accept, then log the breakfast Entry | Meal-classified Entry logged after acceptance | Breakfast Recommendation disappears (slot filled); lunch/dinner unaffected | N/A |
| Decline, then reload same day before 10am | No persisted record of decline | Offer card may reappear (accepted tradeoff, not a bug) | N/A |
| Over-Target State | `remainingBudget < 0` | No breakfast-offer card, regardless of hour or acceptance state | N/A |
| Past the 5am-12pm window, breakfast accepted but never logged | Local hour >= 12, accepted earlier today | `breakfast` does not carry over into the midday/evening windows — same as an unlogged lunch | N/A |

## Design Notes

- **Breakfast Recommendation copy (authored, no pre-approved example exists)**: vegetarian — "Try a bowl of oatmeal with berries and a drizzle of honey."; non_vegetarian — "Try scrambled eggs with whole-grain toast and avocado." Matches the existing lunch/dinner copy's register (short, concrete, one dish) and the "supportive, never prescriptive" tone already established.
- **Why two render positions for `BreakfastOfferCard` instead of one**: traced from a genuine tension between EXPERIENCE.md's Component Patterns ("cards are sequential... the log-a-meal ask always renders first; the breakfast offer renders as a second, separate card below it") and its own Key Flow 1 (declining card 1 reveals the Daily view already showing lunch/dinner Recommendation cards, then accepting card 2 makes "a third card appear above the other two"). Read literally, these two passages contradict each other on whether the Recommendation cards are visible before or only after the breakfast offer resolves. The deciding factor: Story 4.3's frozen spec already traced and verified that declining the log-a-meal card *alone* (via `promptDismissed`) immediately reveals the full Daily view, independent of any other pending state — changing that now would retroactively invalidate already-shipped, reviewed work. So the breakfast offer must be resolvable independently of the log-a-meal card, appearing wherever it's still relevant: below card 1 while the prompt is up, above the Recommendation cards once the prompt is dismissed.
- **Why `MEAL_SLOTS` (the exported `["lunch","dinner"]` constant) stays unchanged**: `expectedSlotsForHour()` conditionally prepends `"breakfast"` rather than redefining the constant itself, since `MEAL_SLOTS` is referenced by its own test file and this codebase's convention is never to change an established exported shape's meaning silently.
