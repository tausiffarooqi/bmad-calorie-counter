- (technique) started Morphological Analysis (Deep)
- (idea) Parameter: meal input mode — options: photo upload, free-text description (e.g. 'one double cheeseburger and medium fries with a can of diet soda')
- (idea) Parameter: calorie estimation pipeline — options: photo -> vision recognition -> generated text description -> calorie calc; text -> direct calorie calc; insufficient detail (either mode) -> re-prompt user to retry
- (idea) Parameter: response composition per submission — estimated calories of meal just logged, total calories remaining for the day, one meal recommendation per remaining meal of the day
- (idea) Parameter: time-of-day meal-count logic — submission 7-10am gives 2 recommendations (lunch+dinner); submission 12-5pm gives 1 recommendation (dinner); implies a mapping of time windows to remaining meal slots
- (idea) Parameter: entry classification (meal vs snack/beverage) — auto-detect whether an entry is a full meal or a snack/tea/coffee; snacks update remaining calories but do not decrement the remaining meal-recommendation count
- (idea) Parameter: recommendation content driver — MVP uses a single account-level dietary preference (vegetarian vs non-vegetarian) set on the account page; deferred: finer-grained preferences (macros, cuisine, allergies, etc.)
- (idea) Parameter: daily target & day boundary — day runs on user's local timezone, from 5am to 12pm; daily calorie target set by user on preferences page, defaulting to a standard adult daily intake
- (question) Day window stated as 5am-12pm (noon) — confirm whether that's intentional (a ~7hr tracked window) or meant to be 5am-12am (midnight, full day)
- (decision) Correction: day boundary is 5am to 12am midnight (not 12pm noon)
- (idea) Parameter: sensitive-data surface — daily calorie target and actual daily intake are personal/sensitive data the user may not want shared, even if not classic PII
- (idea) Parameter: credential protection — email/password login credentials need protection
- (idea) Parameter: photo-content risk — users might accidentally upload personal (non-meal) photos; mitigate via an in-app warning/instruction to only upload meal photos
- (idea) Parameter: threat model — primary concern is bad actors harvesting personal data for ad-targeting/marketing, not just generic account takeover
- (idea) Combination (entry classification x recommendation driver): snacks/beverages never get their own recommendation (veg/non-veg driver only applies to meals); a snack's calories are simply subtracted from the remaining daily budget, shrinking the calorie allotment left for the remaining meal recommendations
- (idea) Refined time windows: 5am-12pm gives 2 recommendations (lunch+dinner); 12pm-10pm gives 1 recommendation (dinner) — closes the earlier gaps
- (idea) After 10pm: only give a meal recommendation if the user hasn't yet met their daily calorie target; if they have, no recommendation is given
- (idea) Over-target handling: once the user has exceeded their daily calorie target (any time of day, not just after 10pm), stop giving meal recommendations entirely and instead report the excess calories consumed
- (decision) Confirmed: over-target rule (stop recommendations, report excess) applies at any time of day, not just after 10pm
- (technique) started Job to Be Done (Structured)
- (idea) First-login-of-day flow: on first login each day, show remaining calories for the day and ask whether the user wants to log a meal now
- (idea) If user declines to log a meal at first login, the app still shows recommendations for the remaining meals of the day based on current progress
- (idea) If first login of the day is before 10am, additionally ask whether the user wants a breakfast recommendation
- (decision) Confirmed: breakfast is a separate third meal slot, on top of lunch+dinner (not one of the 2 recos from the 5am-12pm window)
- (idea) First-login flow includes a tone-adaptive message based on prior day's performance: congratulatory/confidence-building if within daily max, supportive/encouraging (not shaming) if they exceeded it
- (decision) Scope decision: no social/accountability features for now — solo, private experience
- (insight) Current alternative to this app is guessing — most people have no structured way to estimate what they've eaten or decide what to eat next; the app's core value is replacing that guesswork with a concrete estimate + actionable recommendation
- (decision) MoSCoW: Must = A (input/recognition), B (calorie tracking/response), C (recommendation logic), D (daily target/day boundary). Should = E (first-login/daily engagement flow). Could = F (account/security) -- prototype stage, not a hard requirement, but include opportunistically if low-hassle (credential protection, sensitive-data handling, photo-only warning, ad-targeting threat model all bucketed together at Could). Won't-this-time = G (Telegram/WhatsApp, fine-grained diet prefs, social features)
- (insight) Synthesis: core loop is submit->estimate->remaining budget->recommend (photo/text input). Snacks reduce budget without claiming a rec slot. Time windows settled at 5am-12pm (2 recos) / 12pm-10pm (1 reco) / after-10pm conditional / any-time over-target override. Breakfast is a separate opt-in 3rd slot from the first-login flow. The over-target real-time rule and the tone-adaptive daily message are the same 'coaching layer' pattern applied at two moments (in-the-moment vs retrospective) -- treat as one design principle. Snack-vs-meal classification and veg/non-veg recommendation driver are the same classify->conditionally-recommend pattern at two levels (entry vs account). Core value prop: replacing guesswork with concrete estimate + actionable recommendation. MVP scope chosen: Must = input/recognition, calorie tracking/response, recommendation logic, daily target/day boundary; Should = first-login daily engagement flow; Could = account/security (prototype stage); Won't-this-time = Telegram/WhatsApp, fine-grained diet prefs, social features
